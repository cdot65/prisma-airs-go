## Correctness — what I probed and found sound

- **Fixture fidelity.** `aisec/runtime/testdata/directional-security-profile.json` is line-for-line identical to `prisma-airs-sdk/test/models/fixtures/directional-security-profile.json` (276 lines, identical at every sampled offset). It carries all the brief's traps: `database-security: null` (prompt only, `:40`), response model-protection omitting prompt-injection (`:110-119`), tool-response DLP omitting `mask-data-inline` (`:207-216`), `"id": ""` (`:34`), `"agent-protection": []`, `{}` URL categories, compound action `"high:block, moderate:allow"`, and `enable-full-conversation-inspection: false`.
- **Field parity with `mgmt-security-profile.ts` is complete.** I walked all 14 Zod schemas field-by-field against `models.go`; every field is typed, and Go's `omitempty`/nullable choices now mirror TS optionality and nullability exactly. The four `profile:"nullable"` tags (`DataLeakDetectionConfig.Member`, `DataProtectionConfig.DatabaseSecurity`, `URLCategoryMember.Member`, `TopicArrayConfig.Topic`) are exactly TS's nullable set — so the doc claim at `directional-security-profiles.md:35` is accurate.
- **Pre-decode null rejection is the right mechanism.** `encoding/json` sets a `*ProfilePolicy` to nil on `null` without calling `UnmarshalJSON`, so a parent-level check is the only way to reject it. `validateProfileField` (`profile_json.go:217`) runs before `Decode` on every known field and closes that hole; `{"policy":null}` and `{"content-type-configurations":{"prompt":null}}` are both rejected (`profile_json_test.go:224,230`).
- **Nested malformed known fields do fail.** I traced every struct field reachable from `SecurityProfile`; all 23 have `UnmarshalJSON`, so parent-level object-shape validation plus recursive decode gives full depth coverage. No known field can land in extension storage — extensions are only the residue after `delete(object, field.name)` (`profile_json.go:206`).
- **Large numbers.** Extensions and `ModelProtectionConfig.Options` stay `json.RawMessage` and re-emit byte-exact; `Rule1`/`Rule2` `map[string]any` decode with `UseNumber` (`:197`). Tested with 21-digit literals at four nesting levels (`profile_json_test.go:143,149,153,186`).
- **Extension collisions cannot shadow typed fields** (`profile_json.go:166`), including when the typed field is omitted — pinned at `profile_json_test.go:172-182`.
- **Failed re-decode is atomic.** `unmarshalProfileObject` decodes into a fresh local and only assigns `*v = X(next)` on success, so a rejected payload leaves the target untouched; a successful re-decode clears obsolete fields, presence, and extensions. Pinned at `profile_json_test.go:200-220`.
- **`JSONPresence(99)` and unknown presence names fail at marshal** (`profile_json.go:156,160`), surfaced as `aisec.UserRequestPayloadError` before any token/API I/O, with `calls.Load() != 0` asserted (`profile_client_test.go:161`).
- **No invented routes, no pin churn.** `GetByID` still uses the existing paginated list lookup (`client.go:192`); `specs/manifest.json` and all schema snapshots are untouched.
- **Value-receiver `MarshalJSON`** (not pointer) — correct choice, so slice elements and non-addressable values marshal properly.

## Findings

**1. `Extensions` is nil after decoding an object with no unknown fields — adapter panic risk.** `profile_json.go:208` sets `state.Extensions` only `if len(object) > 0`. `directional-security-profiles.md:85-88` tells the Terraform adapter to "keep these maps in provider state and restore them," but writing to a nil map panics. The test that mutates extensions (`profile_json_test.go:172`) only works because that detector happens to have a `future-detector` key. Either always allocate on decode, or add an `EnsureExtension`/setter, or state the nil case in the guide. *Medium — most likely real-world failure mode of this API.*

**2. Promoted `MarshalJSON`/`UnmarshalJSON` hijack consumer embedding — undocumented.** Because these methods are on exported types, `type providerProfile struct { runtime.SecurityProfile; Extra string }` silently serializes only the embedded profile and drops `Extra`. Given the brief's Terraform-adapter focus, this deserves a one-line warning next to the `==` note at `directional-security-profiles.md:5-7`. *Medium-low.*

**3. `ModelProtectionConfig.Name`/`Action` gained `omitempty` — undocumented wire change.** `models.go:128-129`; the only legacy tags altered. It correctly mirrors TS (`ModelProtectionItemSchema` marks both optional, unlike agent/database/malicious-code items), and it is *not* needed for round-trip fidelity (decoded zero values are omitted anyway via `decoded=true`). But a legacy caller constructing `ModelProtectionConfig{Name: "x"}` previously sent `"action": ""` and now omits it. Release notes claim "existing keyed literals … remain compatible," which holds for source but not for this wire detail. *Low — add one line to the migration guide.*

**4. `FieldPresence` cannot distinguish an unknown name from an omitted known field.** `profile_json.go:128` returns `JSONOmitted` for both, and `TestProfileExtensionPresence` now pins that. The marshal path errors on unknown presence names, so the write path catches typos but the read path does not — a mistyped `"mask_data_inline"` reads as omitted and a provider would normalize a live value away. Consider a second return value or a sibling `HasField`. *Low.*

**5. `JSONPresent` override on a nil nullable slice silently becomes `null`.** `profile_json.go:97-101`. `directional-security-profiles.md:57` documents the inverse (non-nil value over a decoded null) but not this coercion. *Low.*

**6. `SecurityProfileListResponse` has no extension preservation** (`models.go` — no embedded `ProfileJSON`). A future sibling of `ai_profiles`/`next_offset` is dropped. Arguably outside the stated "profile model boundary," but worth a decision. *Low.*

**7. Reflection metadata is recomputed on every marshal/unmarshal.** `profileJSONFields` (`profile_json.go:78`) allocates a slice per object, and `marshalProfileObject` builds two maps plus a per-field `json.Marshal`. On `ListAll` over large tenants this is a per-detector cost. A `sync.Map` cache keyed by `reflect.Type` would be a contained fix. *Low — performance only.*

**8. `validateProfileRequest(req any)` double-marshals and is untyped.** `internal.DoMgmtRequest` already marshals before any token acquisition (`mgmthttpclient.go:142`), so the real benefit is reclassifying the error from `AISecSDKInternalError` to `UserRequestPayloadError` — which is correct and matches TS, but the docs oversell it as "before OAuth or API I/O" when the ordering was already safe. Every profile write now serializes the policy twice. `any` also means a wrong argument type passes silently. *Low.*

**9. Test gaps vs. the TS spec.** The TS suite rejects `'content-type-configurations': []` and `{response: []}` (array where object expected). Go rejects both correctly by inspection (`validateProfileField` struct case), but neither is pinned. *Low.*

**10. Repo convention pending.** `docs/developer/feature-quality.md` has a row per feature group and `AGENTS.md` points to it; no row was added for this work. Expected to follow this review.

## Scores

**Implementation standards — 8.5/10.** The presence/extension design is the right shape: value-receiver marshalers, copy-on-write presence maps, atomic decode, parent-level null validation, no hand-rolled transport, stdlib-only, errors via `aisec.WrapError` with the correct `ErrorType`. It survived every edge case I could construct. The deduction is for API ergonomics and cost rather than correctness: the nil-`Extensions` panic surface (#1), the embedding hazard (#2), `FieldPresence`'s lossy unknown-name result (#4), uncached reflection (#7), and the untyped double-marshal validator (#8). There is also an inherent maintenance cost in replacing `encoding/json`'s struct path for 23 types with one reflection layer — justified by the requirement, but it means every future field addition depends on the `profile:"nullable"` tag and the hand-written method wrapper being added correctly, with nothing enforcing that a new type gets its three methods. To reach 9.5: allocate or guard `Extensions`, cache field metadata, and add a test (or generator check) that every `ProfileJSON`-embedding type has `MarshalJSON`/`UnmarshalJSON`/`FieldPresence`.

**Spec fulfillment — 9/10.** Every row of the brief's contract table and all seven implementation items are met, including the two the brief singled out as insufficient if skipped: presence information is genuinely reachable by the adapter (`SetFieldPresence`/`ResetFieldPresence`/`FieldPresence`/`Extensions`, all in the generated reference), and request validation is classified as a user payload error before I/O. Field parity with the TS model is exact, provenance is recorded separately from frozen pins (`testdata/directional-profile-provenance.json`), and no GET-by-ID route was invented. Deductions: the two untested negative cases (#9), the list-envelope gap (#6), and one evidentiary limit worth naming plainly — `profile_client_test.go:40` asserts the create request body equals the complete POST *response* (audit fields, `revision`, `profile_id` included). That is exactly the replay the brief authorized, so it is not a defect, but it means there is still no evidence about which fields a real create omits; the brief's "account separately for audit fields omitted deliberately by a request model" is satisfied only because no request model omits any. To reach 9.5: pin the array-where-object cases and note the audit-field replay limitation in the acceptance record.

**Documentation — 8.5/10.** `docs/developer/directional-security-profiles.md` is genuinely good: the construction table maps each wire intent to a concrete call, the Terraform section states the three-state rule explicitly, forward-compatibility and ownership semantics are covered, and the evidence section separates observed contract from frozen OpenAPI and states the release gap honestly. The runnable example, release note, `runtime-api.md` pointer, regenerated reference (all new types and methods present), sidebar entry, and navigation-spec URL are all wired. Deductions: the three undocumented behaviors above — nil `Extensions` (#1), consumer embedding (#2), the `ModelProtectionConfig` `omitempty` wire change (#3) — plus the unstated `JSONPresent`-on-nil-nullable coercion (#5). The presence prose (lines 51-64) is also dense enough that an adapter author may miss the "assigning false alone cannot express intent on a decoded omitted bool" rule, which is the most consequential sentence in the file. To reach 9.5: add the three missing warnings and promote that bool rule into the table.
